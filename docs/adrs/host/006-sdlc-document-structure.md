# ADR-006: SDLC Document Structure

**Audience:** `host` — see [ADR index](../index.md).

**Date:** 2026-06-23
**Status:** Accepted
**Related features:** All features

## Context

The repository has two audiences for documentation:

1. **Agents and team members during development** -- specs, plans, tasks, ADRs, research, test reports. These are process artifacts that drive the SDLC workflow (SPEC -> PLAN -> TASKS -> IMPLEMENTATION). They are reviewed, iterated on, and referenced by both humans and AI agents throughout the development lifecycle.

2. **Users and operators after shipping** -- developer guides, migration guides, API references, onboarding documentation. These are consumed by customers, partners, and community contributors who deploy and operate the product.

Previously, both types lived in `specs/` and `docs/` at the repo root, making it unclear which documents were process artifacts vs user-facing, and scattering SDLC content across multiple directories.

## Decision

### `.sdlc/` for process artifacts

All documents generated or consumed during the development lifecycle live under `.sdlc/`:

```
.sdlc/
├── specs/           Feature specifications (spec.md, plan.md, design.md, tasks.md)
├── adrs/            Architecture Decision Records (numbered, append-only)
├── research/        Research and investigation reports (numbered)
└── speckit-workflow-guide.md
```

This includes any document that:

- Is generated by an agent (specs, plans, task breakdowns, ADRs, research)
- Requires team review before or during implementation
- Drives the SDLC workflow (speckit commands operate on `.sdlc/`)
- May become stale after the feature ships (plans, task lists)

### `docs/` for user-facing documentation

All documentation intended for end users, operators, and external contributors lives under `docs/`:

```
docs/
└── guides/          Developer guides, migration guides, operational docs
```

This includes any document that:

- Is read by someone deploying or operating the product
- Should stay current after the feature ships
- May be referenced from upstream public repos or product documentation
- Agents should reference when implementing features that affect documented behavior

### Agent behavior

- When creating SDLC artifacts (specs, plans, ADRs, research), write to `.sdlc/`
- When implementing features, check `docs/` for user-facing documentation that may need updating
- When a feature ships, consider whether any `.sdlc/` content should produce a corresponding `docs/guides/` entry (migration guide, developer guide)
- The `/speckit.*` commands operate exclusively on `.sdlc/specs/` and `.sdlc/adrs/`

## Alternatives Considered

### Keep `specs/` and `docs/` at root (status quo)

Flat structure, no nesting. Process and user docs mixed in `docs/`. Agents must infer which docs are process artifacts vs user-facing.

Rejected: Breaks discoverability. New contributors don't know where to put things. Agents scan unrelated files.

### Use `docs/sdlc/` subdirectory

Nest SDLC under `docs/`. Keeps everything under one root.

Rejected: `docs/` implies user-facing content. Nesting process artifacts under it sends the wrong signal about audience.

### Phase-based structure (`1-spec/`, `2-design/`, `3-code/`)

Number directories by SDLC phase.

Rejected: Too rigid. Features don't move linearly through phases. ADRs and research span multiple features.

## Consequences

### Positive

- Single location (`.sdlc/`) for all process artifacts -- agents scan one root
- Clear separation of audience: `.sdlc/` = team, `docs/` = users
- Speckit commands have a predictable, consistent root directory
- Dot-prefix signals "tooling/process" (consistent with `.claude/`, `.specify/`, `.github/`)

### Negative

- Dot-prefix hides the directory in `ls` output (visible with `ls -a` and on GitHub)
- Existing links from external systems (Jira tickets, Slack messages) to old `specs/` and `docs/adrs/` paths will break
- Contributors familiar with the old layout need to learn the new convention
