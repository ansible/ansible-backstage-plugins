# Automation Content UI conversion playbook

**Scope:** Convert Tina's execution-environment (EE) definition catalog, EE image catalog/details, and Ansible Collections catalog/details into the `automation-content` new-frontend-system plugin. Preserve the prototype's content and task flows, but use `@backstage/ui` (BUI) 0.19.x for UI. This is the implementation contract for the UI lanes.

## Page contract and information hierarchy

The plugin is mounted with `noHeader: true`; the host portal's global header is already present. Do not add a second global/page shell or duplicate the portal header. Wrap each route's content in one BUI `Container` (or a full-width `Box` only where a table/card grid must use all available width); do not use legacy `Page`/`Content` or `PluginHeader` as a replacement page shell.

Prototype surfaces reviewed: `CatalogContent.tsx`, `ImagesCatalogPage.tsx`, `EEDetailsPage.tsx`, `CollectionsListPage.tsx`, `CollectionsCatalogPage.tsx`, `CollectionDetailsPage.tsx`; EE cards (`AboutCard`, `DefinedContentCard`, `ResourcesCard`, `ReadmeCard`, `CollectionCard`, `Favourites`, `BreadcrumbsNavigation`, `Header`); and common `PageHeaderSection`. Related source reviewed for layout/state: collection cards, badges, README/about/resource cards, empty state, EE create empty state, and styles.

Hierarchy to retain:

- **EE definition catalog:** short explanatory intro → favorites/owner/tag filters → title + total count, search, sortable/paged table → row-level favorite and actions menu. When the catalog itself is empty, show the create-definition illustration/message and its primary create action instead of an empty table.
- **EE image catalog:** title/count and searchable, paged image table → image details with breadcrumbs, name/favorite, primary “Use in Controller” action → Overview / Collections / (when available) Definition file tabs. Overview emphasizes registry/status/signing/origin and pull reference; collections tab is a table.
- **EE definition details:** breadcrumbs → name/favorite and Actions menu → Overview tab → README as the main reading surface, with Links (download-experience only), About, Defined Content, and Resources in a supporting column.
- **Collections catalog:** Collections title, short description/help, permission-gated Sync Now and sync progress → favorites/search/source/tags/latest-version filters → count → responsive collection cards → pagination. Distinguish an unconfigured/empty catalog from no filter matches and from a page without starred results.
- **Collection details:** breadcrumbs → full collection name + repository trust badge + description + View Source → Overview / Content / Execution Environments tabs. Overview has README plus About/Resources; content and EE relationships are tables. Detail/module pages retain metadata first, then examples/return values.

## Component mapping

All new visual components come from `@backstage/ui` or semantic HTML wrapped by BUI primitives. Preserve domain hooks/services where needed, but do not carry forward legacy UI components (for example, `CatalogFilterLayout`, `UserListPicker`, core-components `Table`, or `MarkdownContent`) when they would render old UI. Reconnect `useEntityList`/catalog APIs to BUI-controlled fields and table state instead.

### Table cell patterns

Use the table data model to render: name (`CellText` and row header), owner, description, up to three tags plus a `+N` indicator, then actions. For long descriptions, do not show an essential full value only in a tooltip: use `Text truncate` with a visible expand action, or allow wrapping in a wider detail view. For action controls in a cell, return `<Cell><Flex ...>…</Flex></Cell>`. Add `aria-label` to favorite/action icons; do not make the whole EE row clickable when it contains menus, favorite controls, or links.

For collection content/EE relationship tables, retain the prototype's name, availability/status, source, registry, publisher/signing, and content columns as present. On narrow viewports, prioritize the identity/status columns and allow the table container to scroll horizontally rather than compressing labels and values into unreadable cells. The BUI Table's `CellText` can place secondary explanatory text beneath a primary value.

## Page layout recipes

### A. Catalog list with filters and table (EE definition files)

1. `<Container>` is the page's only shell. Place the short purpose copy before the data area when results exist; set it as `Text body-large as="p"` with a comfortable max width.
2. Desktop: `<Grid.Root columns={{ initial: '1', lg: '12' }} gap="4">`; use `<Grid.Item colSpan={{ initial: '12', lg: '3' }}>` for a `Flex direction="column" gap="3"` filter stack and the remaining `9` columns for content. Mobile: naturally stack the filters before results; do not hide them. Use `Flex align="start"` within grid items when alignment is needed.
3. Filter stack: visible “Favorites” selection (All/Starred), Owner `Select`, Tags `Select`. Owner/tag options come from the catalog facet APIs; changes update the existing entity filters and preserve server-side behavior. Use `SearchField` in the table header or BUI Table search binding.
4. Content header: `Flex justify="between" align="center"` with “Execution Environment definition files” and the total count; place a BUI `SearchField` bound to `useTable` search state and then the table below. Use BUI `Table` with offset pagination bound to current `limit`/`offset`.
5. Row menu: favorite + `MenuTrigger`/`Menu` action control. Keep Build only when buildable, Edit/View Source as applicable, Download/Delete for download experience. Destructive Delete is visually destructive and opens a confirmation dialog.
6. First-run empty catalog: show the existing creation guidance and primary “Create execution environment definition file” button, with the illustration as optional supporting content. On mobile stack copy/action first, illustration second; illustration is decorative if the copy already conveys meaning (`alt=""`).

### B. Catalog list with cards (Collections)

1. `Container` → `PageHeaderSection` composition: `Flex direction={{ initial: 'column', md: 'row' }} justify="between" align="start" gap="4"`, heading `Text title-large as="h1"`, concise help hint, description, and permission-gated Sync Now `Button variant="secondary"`. Use a tooltip only for a short hint; place sync progress/last-sync details in a small adjacent status region or a keyboard-operable `Menu`/`Popover`, not hover-only tooltip content.
2. Desktop: 3-column BUI grid for left filters and 9-column content. Mobile: filter stack above results (or a BUI `Accordion` named “Filters” if vertical space warrants; preserve all filter controls and current selections). Filters: `SearchField`, favorites (all/starred), source `Select`, tags `Select`, `Checkbox` “Show latest version only”.
3. Content heading is “Ansible Collections” + correct result count; show a subtle inline updating state for page changes while keeping prior cards visible. Render cards in `Grid.Root columns={{ initial: '1', md: '2', xl: '3' }} gap="4"`.
4. Collection card order: full `namespace.name` + Certified/Validated/Community badge + favorite button; version `Tag`/`Badge`; source link or source text; last sync anchored at the card bottom. Make the card link semantic (`Card href` + accessible label), but keep favorite and external source links independently interactive.
5. Pagination below grid: visible result range and page number plus named previous/next buttons. Keep starred count wording distinct when the favorites filter is active.

### C. Details page with cards and tabs

**EE definition:** breadcrumbs → header/favorite + actions menu → Overview tab → desktop 8/4 layout (README left, Cards right); at narrow widths stack README first, then Links/About/Defined Content/Resources. The right column's children use `Flex direction="column" gap="4"`. README can scroll inside its card when lengthy; page itself remains normally scrollable.

**Image details:** breadcrumbs → `Flex` with image name and “Use in Controller” primary CTA → Tabs. Overview is a metadata Card: `Grid.Root columns={{ initial: '1', md: '2' }} gap="3"`, label/value pairs, then a separated pull reference with copy-friendly wrapping. Collections is the relationship table. Definition file tab exists only when a definition exists; within it retain README plus About/Defined Content/Resources. At mobile, header/action stack and metadata labels/values become one column.

**Collection details:** breadcrumbs → title and repository badge row (wrap on mobile), description, View Source secondary action → Overview/Content/Execution Environments tabs. Overview uses a flexible README column plus a roughly one-third supporting stack of About/Resources; stack on mobile. Content/EE tabs use a full-width BUI Table with search and pagination. The no-EE state belongs inside that tab and explains where matching images will appear.

**Module details (where included):** semantic heading/description → metadata card with two-column label/value grid (single column on mobile) → Examples and Return values cards in a two-column grid that collapses to one. Preserve long code/value text in wrapping, horizontally scrollable or `<pre>` areas without forcing the overall page wider than the viewport.

### D. Dialog flows

- **Sync collections / images:** dialog title and explanation; list of registry/source checkboxes; “Select all” in a clear secondary position; footer with Cancel and primary “Sync selected”. Disable confirm when none selected; show pending state and prevent accidental double submit. For collection-source sync, show per-source progress and failures in the page context after submit.
- **Use in Controller:** title → explanation → prefilled EE name, read-only pull reference, Organization `Combobox`/`Select`, Description `TextAreaField`, inline error, footer Cancel + “Use in Controller”. Keep the image name/context visible; focus first field when opened; preserve user edits if the dialog remains open after a recoverable error.
- **Unregister/Delete / build or authentication:** explain the consequence and exact target in dialog text. Put Delete in BUI destructive styling and require explicit confirmation; don't use a tooltip. A busy auth/build step must be announced and cannot leave focus behind a non-interactive overlay.
- For every dialog, use controlled BUI `Dialog`; title/header, body, and footer sections. Keep focus contained, Escape behavior predictable, and focus returned to the trigger on close (BUI handles dialog primitives; do not add custom focus code unless a test shows a host integration gap).

## Loading, empty, and error states

| Situation | Standard recipe |
| --- | --- |
| Initial table fetch | Render BUI Table with `isPending` so headers/pending rows retain the final geometry. If the table can't be rendered until data arrives, show a heading skeleton plus 3–5 row-shaped skeletons. Set `aria-busy` on the results region. |
| Initial card fetch | Render 3–6 card skeletons in the same responsive grid as loaded cards, with title/version/source/last-sync lines. Avoid a centered spinner that makes the whole catalog jump after load. |
| Detail fetch | Skeleton breadcrumb/title/action and matching card/metadata skeletons; keep the page shell and widths stable. If only README is reloading, skeleton only that card and leave About/data visible. |
| Background page/filter refresh | Keep current results visible; mark the region `aria-busy`; disable/guard only controls that cannot safely be used. Keep pagination/favorite semantics consistent. Do not fade the entire page to near-invisible contrast or set `inert` on all content without a clear interaction reason. |
| Truly empty catalog | Custom composed empty state with specific title, short explanation, and relevant action: Create EE definition or Sync catalog (only when permission allows). For no configured sources, explain admin next step; do not imply clicking Sync will fix configuration. |
| No filter/search matches | Keep filters and search visible; show “No collections match your search or filters” plus a clear-filters action where possible. Do not replace it with the “No collections found/configured” empty-catalog state. |
| No starred items on page | Explain that the current page contains no starred items and allow browsing other pages or return to All; do not claim no favorites exist globally if pagination limits the evidence. |
| No relationships | Use a local empty panel in the relevant tab (“No collections included…” / “This collection is not included…”). Keep breadcrumbs/header/tabs intact. |
| Request failure | Show inline error with `role="alert"`, a plain-language summary, and Retry using BUI Button. Preserve existing filters/page where possible. Do not render raw `Error: ${error}` as the only error UX. Distinguish not-found from failed-to-load. |
| Dialog submission failure | Keep dialog open, show inline error near fields/actions, preserve form values, clear pending state and restore the primary action. Do not close then hide the failure in a transient notification. |

## Design tokens and theming

- Load the BUI stylesheet once at the host/plugin integration boundary: `@backstage/ui/css/styles.css`. Do not import a second competing theme or add the old MUI baseline for these pages.
- Use BUI spacing utility props and responsive values (`p`, `px`, `mt`, `gap`, etc.; the documented scale includes `0.5`, `1`, `1.5`, `2`, `3`, `4`, etc.). Prefer page rhythm around gap `4`, dense control gaps `2`, and larger section gaps `6`; don't mechanically convert each MUI spacing call.
- Use BUI semantic text colors (`primary`, `secondary`, `success`, `warning`, `danger`) and provider backgrounds (`neutral`, `success`, `warning`, `danger`) only when semantic meaning is intended. Keep neutral surfaces and component colors owned by BUI. If a custom CSS rule is unavoidable, use documented BUI CSS variables (e.g. neutral/background/foreground/status token families) rather than literal hex/RGB values; verify token names against the installed 0.19.x stylesheet before use.
- Do not inspect `theme.palette.type`, branch on light/dark, or hardcode color values. The BUI stylesheet and host theme supply dark-mode colors, surfaces, focus, borders, and component states.
- Keep custom CSS structural: responsive widths, scroll containment, markdown/code wrapping, or a one-off text truncation. Avoid overriding `.bui-*` internals or recreating shadows, radii, hover colors, status palettes, or focus rings.
- The installed worktree resolves `@backstage/ui` **0.19.0**. Some online component pages may describe a later/older API generation; implementation must follow the installed package's types and tokens. In particular, BUI provider backgrounds use the installed generation's `bg="neutral" | "success" | "warning" | "danger"` API, not old `surface` or MUI theme values.

## Accessibility acceptance rules (WCAG 2.1 AA)

- **Semantic structure:** one `h1` per route, ordered `h2`/`h3` sections, `<nav aria-label="Breadcrumb">`, and `<main>` ownership supplied by the route/host. Do not introduce a second `<main>` if the host already provides it.
- **Keyboard/focus:** every link, button, checkbox, select, menu item, tab, and card overlay is keyboard reachable. Preserve BUI visible focus indicators; never remove outlines. Icon-only controls need specific accessible names. Ensure nested CollectionCard favorite/source controls remain distinct from the card link.
- **Tabs:** use BUI's tab pattern so arrow keys, selected state, and panel relationships are managed correctly. URL/query-param changes must not break keyboard selection or panel identity. Keep disabled/unavailable tabs out of the tab order where not relevant.
- **Tables:** use BUI Table's keyboard-accessible sorting/pagination; mark primary entity name as `isRowHeader`; give search a visible label or `aria-label`; announce counts/empty results. Each row's favorite/menu actions need row-specific labels. Never make clickable table cells the only way to reach an action.
- **Dialogs/menus:** retain focus management, Escape/close affordance, focus return, and menu keyboard navigation. Close a menu before opening a modal. Destructive confirmation must name the resource and effect.
- **Contrast/trust signals:** body text contrast ≥4.5:1; large text and meaningful non-text controls ≥3:1. Certified/Validated, signing, sync, and image status must always include visible words (and optionally icons), not color alone. Use semantic BUI status colors rather than hand-picked badge colors; verify final theme contrast in both light and dark modes.
- **Motion/updates:** respect reduced motion; no custom spinning icon unless motion is reduced appropriately. `aria-busy` accompanies loading regions; use a polite live region for sync completion/failure and actionable status updates, not for every skeleton.
- **Links/README:** external new-tab links use `rel="noopener noreferrer"`; distinguish link from button action. Preserve the existing sanitization boundary for upstream HTML README data; don't render untrusted HTML directly.

## Do not use

- Any `@material-ui/*` import, MUI component, `makeStyles`, `withStyles`, `useTheme`, or copied `.Mui*` selector in new page code.
- Legacy `@backstage/core-components` UI (`Page`, `Content`, `Progress`, `InfoCard`, `EmptyState`, `Table`, `MarkdownContent`) or MUI-rendering `CatalogFilterLayout`/`UserListPicker` in the converted presentation layer.
- Hard-coded hex/RGB colors, MUI theme palette/spacing values, custom light/dark branching, or status color styling copied from prototype chip helpers.
- Inline styles for repeated layout or visual design; use BUI spacing/display/width props and a local CSS module only for legitimate structural gaps. No hard-coded pixel spacing/radius where a BUI spacing/sizing token or primitive exists.
- Hover-only essential text, tooltip-only explanations of disabled actions, color-only status/trust indicators, non-semantic clickable `<div>` cards, placeholder `href="#"`, clickable rows with nested action conflicts, or unlabeled icon controls.
- Fixed widths/heights that cause clipping; do not reproduce the old 400px sync-dialog minimum width or fixed 320px card layouts on mobile. Use BUI responsive props and content-aware sizing.
- Hand-built focus traps, manual menu anchoring, or a page-level backdrop spinner to imitate MUI behavior when BUI primitives already provide the interaction.

## Suggested improvements for orchestrator decision

1. **Replace hover-only full-description tooltips.** The EE table truncates long descriptions and exposes the full text via Tooltip. Prefer a visible “Show full description” disclosure (or a wider detail view) so keyboard/touch users get the same information. This changes the interaction, not the metadata hierarchy.
2. **Make collection cards genuinely semantic links.** The prototype's clickable Card `<div>` uses `onClick` and manually stops propagation for nested controls. BUI Card supports a labeled `href` overlay with nested independent controls; use it to fix keyboard, open-in-new-tab, and nested-action behavior while preserving the same visual scan order.
3. **Confirm whether image-list and image/collection relationship data are real or prototype-only.** `ImagesCatalogPage.tsx` has local sample records/mock collections and simulated sync notifications. Reuse the UI structure, not fabricated records or success behavior; wire only to the real `automation-content` data/actions that the implementation lane owns.
