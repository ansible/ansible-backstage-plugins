# Publishing a Portal SDK developer preview

## Release boundary

`sdk-package-publish.yml` publishes the ten SDK, host and frontend authentication
packages in `packages.json` directly from this repository. Feature plugins and
dynamic OCI artifacts are outside this workflow. Every package in a release uses
the same explicit `0.y.z-alpha.N` version and the npm `next` distribution tag.

The workflow runs manually on `main` in `ansible/ansible-backstage-plugins`.
Its build job tests the repository, builds and packs the candidates, exercises
the isolated consumer, and generates SBOMs without OIDC permissions. The publisher
uses a separate GitHub-hosted runner behind the `npm-preview` environment. It
revalidates the archives against the source revision and SHA-256 digests, signs
their provenance, and publishes those same archives in dependency order. It
does not rebuild packages or run their lifecycle scripts with publishing access.

Authentication uses npm trusted publishing through GitHub OIDC. There is no
npm token secret or token fallback configured. The publisher uses empty user and
global npm configuration files and runs outside the checkout. It rejects static
authentication environment variables. npm registry provenance is generated by
`npm publish --provenance`, separately from the retained GitHub attestation bundle.

## Automated security gates

The read-only build job must pass both gates before handing archives to the
publisher. The preview policy blocks **all reported findings**, without automatic
exceptions. Missing, incomplete, failed or inaccessible scans also block release.

- **SAST:** Reuse the repository's completed CodeQL analyses for the exact release
  commit on `refs/heads/main`. Require JavaScript/TypeScript and Actions categories,
  inspect their SARIF results, and reject any reported result at any severity.
  A successful analysis job alone does not establish a clean result. The gate
  waits up to ten minutes for matching analyses, never substituting another SHA.
  Existing findings must be resolved before publication. This is repository-wide
  SAST, so findings outside the package allowlist can also block release.
- **SCA:** Run the pinned consumer's Yarn audit recursively across its resolved
  production dependencies at severity `info` and above. The consumer declares
  packages, peers and verification tools as dependencies, so this intentionally
  covers that whole installed graph, including its transitive dependencies.
  Deprecation notices are excluded because they are not vulnerability findings.
  Dependency lifecycle scripts remain disabled. No advisory exclusions are added.

The build job requires only `contents: read` and `security-events: read`. It does
not receive OIDC or attestation write permissions. A repository administrator must
keep CodeQL default setup enabled for both required categories on main and allow
the workflow token to read its analyses. No additional personal token is needed.

The `sdk-security-diagnostics` artifact retains CodeQL reports, audit output and
the audited consumer lockfile even when a gate fails. Successful evidence binds
the source SHA, archive hashes and security-report hashes. The publisher verifies
that evidence again and includes it in signed provenance. No artifact handoff or
npm publication happens after a failed security gate.

## Prerequisites

- Maintainers have approved the package scope, public APIs, compatibility baseline,
  dependency/license/security checks and preview release. The workflow's tests,
  SBOMs and attestations do not constitute security approval or live RHDH testing.
- A reviewed release commit on `main` sets all ten candidate versions to the same
  preview version, sets `private: false` and `publishConfig.access: public`, and
  updates the lockfile. Internal dependencies resolve to the matching candidates.
  Existing `workspace:^`, `workspace:~` and `workspace:*` references are supported
  because Yarn rewrites them during packing. No feature package loses its guard.
- Required PR checks pass for that release commit. Protect `main`, require review
  of the workflow and its scripts, and prevent bypass by unauthorized users.
- A repository administrator creates the `npm-preview` GitHub environment,
  restricts deployment branches to `main`, requires maintainer approval, and
  prevents self-approval. The YAML references this environment but cannot create
  or enforce its repository-side protection settings by itself.
- Each npm package exists and has an authorized maintainer. Configure its trusted
  publisher with organization `ansible`, repository `ansible-backstage-plugins`,
  workflow filename `sdk-package-publish.yml`, and environment `npm-preview`.
  Permit `npm publish`. Require 2FA and disallow token-based publishing in package
  settings. Do not add `NPM_TOKEN` or `NODE_AUTH_TOKEN` repository secrets.

### First publication

npm requires a package to exist before its trusted publisher can be configured.
If a candidate name does not exist, stop and agree the bootstrap procedure with
the namespace owners and security maintainers. Any interactive first publication
requires separate approval and must use the reviewed real package. Do not create
placeholder packages or introduce a publishing token as a workaround.

The automated workflow intentionally refuses to publish any candidate until all
package names exist. Package existence alone does not prove the OIDC relationships
are correct. Confirm every configuration before approving the publish job.
This workflow implements subsequent OIDC releases, not an automated bootstrap.

See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) and
[npm trust prerequisites](https://docs.npmjs.com/cli/v11/commands/npm-trust/).

## Procedure

1. Merge the reviewed release metadata and complete the prerequisites above.
2. Open **Actions → Publish SDK preview → Run workflow**. Select `main` and enter
   the exact reviewed version, such as `0.1.0-alpha.0`. The input validates the
   committed version. It does not rewrite manifests or remove private guards.
3. Wait for the build job. Download `sdk-npm-preview` and review its source commit,
   package names, versions, validation report, archive hashes and SBOMs. Confirm
   release-specific security and runtime evidence applies to that source commit.
4. An authorized maintainer approves the `npm-preview` environment deployment.
   The publisher signs the evidence and sends the exact archives to npm under
   `next`. npm version `11.6.4` and Node `22.22.3` are pinned for publishing.
5. Retain the `sdk-npm-preview-signed` artifact, including the provenance bundle,
   for release evidence. It is retained for 30 days in Actions. Copy it into the
   project's approved long-term release storage if longer retention is required.

## Verification

Check the version and tag for each published candidate, for example:

```bash
npm view @ansible/portal-extension-api@next version dist.integrity
```

Verify an archive's signed GitHub provenance after downloading the signed artifact:

```bash
gh attestation verify artifacts/portal-extension-api.tgz \
  --bundle provenance.sigstore.json \
  --repo ansible/ansible-backstage-plugins \
  --signer-workflow ansible/ansible-backstage-plugins/.github/workflows/sdk-package-publish.yml
```

Confirm npm displays registry provenance and install the exact versions into an
independent consumer without local tarball resolutions. Exercise the documented
frontend/backend imports and host integration. The existing packed consumer
validates local archives, not registry propagation or live RHDH behavior.

## Failed and partial releases

npm does not publish this set atomically. OIDC configuration errors or registry
failures can occur after some packages have been published. Signed build evidence
is uploaded even when publication fails after attestation.

Before any registry write, the script checks that all names exist and that none
already contains the requested version. A rerun after partial publication fails
closed. Inspect the registry and release evidence, then agree recovery with the
release maintainer. Do not automatically skip existing versions, unpublish
packages, overwrite `latest`, or force a republish. Prefer a new coordinated
preview version through a reviewed release commit.

## Local validation

The following command does not contact npm or publish anything:

```bash
node --test scripts/sdk-package-validation/*.test.mjs
```

The guard tests cover release metadata, dependency ordering, changed archive and
SBOM bytes, source revision mismatches and refusal to publish outside GitHub OIDC.
Only an approved live workflow run can validate the actual npm trust relationships.
