# Publishing a Portal SDK developer preview

## Release boundary

`sdk-package-publish.yml` publishes the ten SDK, host and frontend authentication
packages in `packages.json` directly from this repository. Feature plugins and
dynamic OCI artifacts are outside this workflow. Every package in a release uses
the same explicit `0.y.z-alpha.N` version and the npm `next` distribution tag.

The workflow runs manually on `main` or a `release-*` branch in
`ansible/ansible-backstage-plugins`. Release branch names must not contain slashes.
Tags and other branches cannot publish. All branches use the same preview version
policy and npm `next` tag.

Its build job tests the repository, builds and packs the candidates, exercises
the isolated consumer, and generates SBOMs without OIDC permissions. The publisher
uses a separate GitHub-hosted runner behind the `npm-preview` environment. It
revalidates the archives against the source revision and SHA-256 digests, signs
their provenance, and publishes those same archives in dependency order. It
does not rebuild packages or run their lifecycle scripts with publishing access.

Authentication uses npm trusted publishing through GitHub OIDC. There is no
npm token secret or token fallback configured. The publisher uses empty user and
global npm configuration files and runs outside the checkout. It rejects static
authentication environment variables. npm registry provenance is generated by
`npm publish --provenance`, separately from the retained GitHub attestation bundle.

## Automated security gates

The read-only build job must pass both gates before handing archives to the
publisher. The preview policy blocks all release-scoped SAST findings and all
dependency findings without a current, reviewed exception. Dependency exceptions
are explicit preview risk decisions, not fixes or evidence that a dependency is
safe. Missing, incomplete, failed or inaccessible scans and findings with
unclassifiable locations also block release.

- **SAST:** Reuse completed CodeQL analyses for the exact release commit and
  selected branch ref, with both JavaScript/TypeScript and Actions coverage.
  `security-scope.mjs` defines the reviewed boundary from the ten package roots
  in `packages.json`, the SDK validation/publishing workflows and scripts, local
  actions, and shared build inputs. Repository source paths found in the exact
  hashed archives' source maps extend the boundary to bundled code from elsewhere
  in the repository. Directory matches respect path boundaries.
  Primary, related and data-flow locations are checked. Any finding touching the
  boundary blocks publication, including notes and warnings. Missing, ambiguous
  or unsupported locations fail closed. Unrelated feature-plugin and workflow
  findings remain in CodeQL under their owning teams and do not block this npm
  release. This is not a dismissal of those findings.
  A successful analysis job alone does not establish a clean scoped result. The
  gate polls up to 60 times, searching up to ten pages of 100 results per poll.
  It never substitutes another branch or SHA, even when branches share a commit.
- **SCA:** Run the pinned consumer's Yarn audit recursively across its resolved
  production dependencies at severity `info` and above. The consumer declares
  packages, peers and verification tools as dependencies, so this intentionally
  audits registry-resolved (`npm:`) dependencies reachable from those packages,
  including transitive dependencies. The SDK candidates themselves are installed
  as local `file:` tarballs and are not submitted to the advisory API. Their source
  is covered separately by SAST and release review.
  Deprecation notices are excluded because they are not vulnerability findings.
  Dependency lifecycle scripts remain disabled. The scanner receives no advisory
  exclusions. Its complete finding report and original exit status are retained.
  `audit-exceptions.json` can accept only the exact reviewed advisory, package,
  affected versions and severity, for the SHA-256 of the reviewed consumer
  lockfile. The assessment records every reported and accepted finding in
  `dependency-audit.summary.json`. A successful assessment can therefore retain a
  scanner exit status of 1 when every finding has an applicable exception.
  Other exit statuses, malformed or inconsistent reports, and unmatched findings
  still fail the release.

The build job requires only `contents: read` and `security-events: read`. It does
not receive OIDC or attestation write permissions. A repository administrator must
ensure CodeQL scans both required categories on every publishing branch and
allow the workflow token to read its analyses. Enable scanning for protected
release branches or explicitly include them in the CodeQL configuration as
appropriate for the repository setup. The publishing workflow does not create
missing scans or fall back to results from `main`. No additional personal token
is needed.

The `sdk-security-diagnostics-<attempt>` artifact contains a sanitized
`scan-status.json` with the source ref/SHA and pass/fail states, the audited
`consumer.yarn.lock`, the complete npm dependency audit output in
`yarn-audit.ndjson`, and `dependency-audit.summary.json` when assessment succeeds.
These dependency diagnostics are retained even when a gate fails so maintainers
can compare the actual resolved graph with the reviewed exception policy.
Raw SARIF, CodeQL finding details, package archives and passing release receipts
are excluded from this diagnostic artifact. Detailed CodeQL findings remain in
the repository's restricted code-scanning interface.
The independent dependency audit still runs after a CodeQL lookup or download
failure. If the job fails before it can write a status file, no diagnostic
artifact may exist; inspect the failed step log instead.

After both gates pass, the successful handoff retains sanitized CodeQL
summaries, analysis metadata, the full audit output, dependency assessment and
audited consumer lockfile.
Summaries contain only finding counts and digests, including the normalized raw
SARIF digest. Raw SARIF and excluded finding details are never uploaded, even on
successful scoped releases. Detailed results remain in restricted CodeQL storage.

The trusted read-only build classifies the complete scan results and binds the
reviewed scope, source branch/SHA, summary hashes and archive hashes in its security
receipt. The publisher recomputes the scope from its reviewed allowlist and exact
archives, checks that receipt and the sanitized summaries, and attests them before
publication. It does not fetch raw CodeQL results with publishing authority.
A receipt for the former repository-wide policy or a different scope is rejected.
No release handoff or npm publication happens after a failed gate.

### Reviewing dependency exceptions

An exception requires an exact advisory identifier, package, affected versions,
severity, owner, rationale, evidence links, creation date and expiry date. Its
disposition distinguishes `not-affected` from `risk-accepted`. An upstream
dependency or a passing package test is not by itself evidence of
non-applicability. Assess the actual dependency version and how supported hosts
and consumers use it. A maintainer statement about a different release line does
not establish that the installed version is unaffected.

Exceptions expire at 00:00 UTC on the stated date and cannot last more than 30
days. There is no automatic renewal. Changes to the consumer lockfile, advisory
severity or affected versions require a new review. Remove unused exceptions
when fixes make them unnecessary. The currently proposed preview decisions
expire on 27 December 2026 and explicitly accept inherited risks, including two
High-severity findings. They are not a production-readiness or security approval.

The read-only build assesses the complete report and records a digest of the
committed exception policy. The protected publisher independently repeats the
assessment against its checkout, the retained audit output, original status and
lockfile. It rechecks expiry immediately before publication. Changed decisions,
expired decisions, tampered summaries and receipts from the former policy are
rejected. SAST has no exception mechanism.

Before merging an exception change, release maintainers review its complete
finding list and any required security approval. The independent `npm-preview`
reviewer then reviews the release-specific assessment before authorizing the
exact archives. Changing the policy does not bypass branch review, protected
environment approval, OIDC, SBOM or provenance checks.

The current risk acceptances cover an integration preview with reviewed plugins,
trusted configured integrations and translation resources, sanitization of
untrusted rendered HTML, and validation of untrusted navigation destinations.
Affected manual SSR/hydration flows and security-sensitive use of inherited FTP,
file-parser or UUID buffer APIs are outside this preview's validated usage.
Consumers must assess these limitations against their own host configuration.

## Prerequisites

- Maintainers have approved the package scope, public APIs, compatibility baseline,
  dependency/license/security checks, any dependency exceptions and preview release. The workflow's tests,
  SBOMs and attestations do not constitute security approval or live RHDH testing.
- A reviewed release commit on `main` or the selected `release-*` branch sets
  all ten candidate versions to the same preview version, removes `private: true`
  and sets `publishConfig.access: public`, and
  updates the lockfile. Internal dependencies resolve to the matching candidates.
  Yarn normalizes `private: false` by omitting the field. Both public forms are
  accepted, while `private: true` and non-boolean values are rejected.
  Existing `workspace:^`, `workspace:~` and `workspace:*` references are supported
  because Yarn rewrites them during packing. No feature package loses its guard.
- Required PR checks pass for that release commit. Protect `main` and every
  publishing release branch, require review
  of the workflow and its scripts, and prevent bypass by unauthorized users.
- A repository administrator creates the `npm-preview` GitHub environment,
  allows only the `main` and `release-*` branch patterns (no tag rules), requires
  approval from `@ansible/automation-portal-engineers` or
  `@ansible/automation-portal-admin`, prevents self-approval and disables
  administrator bypass. The YAML references this environment but cannot create
  or enforce its repository-side protection settings by itself.
- Each npm package exists and has an authorized maintainer. Configure its trusted
  publisher with organization `ansible`, repository `ansible-backstage-plugins`,
  workflow filename `sdk-package-publish.yml`, and environment `npm-preview`.
  Permit `npm publish`. Require 2FA and disallow token-based publishing in package
  settings. Do not add `NPM_TOKEN` or `NODE_AUTH_TOKEN` repository secrets.
  Configure trust during the release window: npm requires the first successful
  publish within two days of creating a trusted publisher. An unused configuration
  expires after that deadline. Delete and recreate expired configurations before
  approval. See [npm trusted publisher expiry](https://docs.npmjs.com/trusted-publishers/#trusted-publisher-configuration-expiry).

### First publication

npm requires a package to exist before its trusted publisher can be configured.
If a candidate name does not exist, stop and agree the bootstrap procedure with
the namespace owners and security maintainers. Any interactive first publication
requires separate approval and must use the reviewed real package. Do not create
placeholder packages or introduce a publishing token as a workaround.

The automated publisher intentionally refuses to publish any candidate until all
package names exist. Package existence alone does not prove the OIDC relationships
are correct. Confirm every configuration before approving an OIDC publication.
The workflow does not perform an automatic first publication.

To obtain reviewed bootstrap artifacts, select `prepare_bootstrap: true` when
dispatching the workflow from the reviewed `main` or `release-*` commit. The
same tests, build, scans, exception assessment and `npm-preview` approval still
run. The protected job revalidates and attests the exact archives, then uploads
`sdk-npm-preview-signed-<attempt>` without invoking `npm publish`.

An authorized maintainer can then perform the separately approved interactive
first publication with `npm login` and 2FA, using those same verified archives
without lifecycle scripts and with the explicitly approved distribution tag.
Do not rebuild or rewrite them locally. The bootstrap must use the same exception
policy and fresh expiry checks as the reviewed release. Local npm publication
does not produce npm's registry-generated OIDC provenance. Retain the signed
GitHub evidence and distinguish it from npm provenance for later OIDC releases.

The first version need not be `0.0.0`. If the reviewed `0.1.0-alpha.0` archives
are used for bootstrap, that version is consumed and the next automated release
must use a new coordinated version. Publishing a separate `0.0.0` bootstrap set
requires separately prepared and reviewed archives with matching internal
dependency versions. Never relabel an already reviewed tarball.

See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) and
[npm trust prerequisites](https://docs.npmjs.com/cli/v11/commands/npm-trust/).

## Procedure

1. Merge the reviewed release metadata and complete the prerequisites above.
2. Open **Actions → Publish SDK preview → Run workflow**. Select the reviewed `main` or `release-*` branch and enter
   the exact reviewed version, such as `0.1.0-alpha.1`. Keep `prepare_bootstrap`
   disabled for an OIDC publication. Enable it only for the reviewed artifact-only
   first-publication procedure above. The version input validates the
   committed version. It does not rewrite manifests or remove private guards.
3. Wait for the build job. Download `sdk-npm-preview-<attempt>` and review its source commit,
   package names, versions, validation report, archive hashes, SBOMs and
   `security/dependency-audit.summary.json`. Confirm
   release-specific security and runtime evidence applies to that source commit.
   Accepted findings are not fixed findings. Verify their rationale, expiry and
   usage restrictions before approving a release.
4. An authorized maintainer approves the `npm-preview` environment deployment
   before the reviewed handoff artifact expires after seven days. If it expires,
   start a fresh dispatch for the reviewed release and review the new handoff
   before approving. Also check that newly configured npm trust has not expired.
   The publisher signs the evidence and successfully uploads the signed artifact
   before sending any archives to npm under
   `next`. npm version `11.6.4` and Node `22.22.3` are pinned for publishing.
5. Retain the `sdk-npm-preview-signed-<attempt>` artifact, including the provenance bundle,
   for release evidence. It is retained for 30 days in Actions. Copy it into the
   project's approved long-term release storage if longer retention is required.

Artifact names include the build or publish attempt number so reruns preserve
earlier evidence. The publish job downloads the exact artifact ID produced by
its successful build, including when only a failed publish job is rerun.

The initial `0.1.0-alpha.0` publication is an integration preview tagged with both
`next` and `latest`. Subsequent preview publications through this workflow update
`next` and leave `latest` unchanged. Use an exact version when reproducing an
integration rather than relying on either moving tag. A package version already
published during bootstrap cannot be reused to test OIDC publication.

## Verification

Check the version and tag for each published candidate, for example:

```bash
npm view @ansible/portal-extension-api@next version dist.integrity
```

Verify an archive's signed GitHub provenance after downloading the signed artifact.
Use a current GitHub CLI supporting `--source-ref` and `--source-digest`.
Set the reviewed branch and commit from the approved handoff, for example:

```bash
RELEASE_REF=refs/heads/main
RELEASE_SHA='replace-with-reviewed-40-character-commit-sha'
gh attestation verify artifacts/portal-extension-api.tgz \
  --bundle provenance.sigstore.json \
  --repo ansible/ansible-backstage-plugins \
  --signer-workflow ansible/ansible-backstage-plugins/.github/workflows/sdk-package-publish.yml \
  --source-ref "$RELEASE_REF" \
  --source-digest "$RELEASE_SHA"
```

Confirm npm displays registry provenance and install the exact versions into an
independent consumer without local tarball resolutions. Exercise the documented
frontend/backend imports and host integration. The existing packed consumer
validates local archives, not registry propagation or live RHDH behavior.

## Failed and partial releases

npm does not publish this set atomically. OIDC configuration errors or registry
failures can occur after some packages have been published. Signed build evidence
is uploaded even when publication fails after attestation.

Before any registry write, the script checks that all names exist and that none
already contains the requested version. A rerun after partial publication fails
closed. Inspect the registry and release evidence, then agree recovery with the
release maintainer. Do not automatically skip existing versions, unpublish
packages, overwrite `latest`, or force a republish. Prefer a new coordinated
preview version through a reviewed release commit.

## Local validation

The following command does not contact npm or publish anything:

```bash
node --test scripts/sdk-package-validation/*.test.mjs
```

The guard tests cover release metadata, dependency ordering, changed archive and
SBOM bytes, source revision mismatches and refusal to publish outside GitHub OIDC.
Only an approved live workflow run can validate the actual npm trust relationships.
